Each of my projects has shipped with invariant tests and a benchmark. An invariant test states what properties or rules should always hold for a specific piece of logic; the benchmark verifies those same rules are being upheld when there is some level of load applied. Anyone can write code that compiles, but verifying that it actually holds up under load is a harder problem.

Order Book Engine

GitHub Live demo
The problem

Every stock exchange ensures that orders are executed according to price-time priority. An order that is best priced will execute first, and when there are two or more orders of equal pricing, the earlier order is executed. This is the assurance which keeps the markets free from unfairness. When it is violated, someone overpaid or waited longer than they should have.

The decision

I created a matching engine that can be proven to maintain price-time priority by using five invariant tests, and also by using a real-time view of the three things a trader typically examines: Level II depth, the depth chart, and the trade tape. By pressing the Market Impact button, a 500 quantity market order is fired into the book to show how a large order sweeps through price levels, consumes liquidity and moves the price. This is why we see slippage on trades.

What I'd change

The simulator runs in JavaScript. A production quality matching engine would require lock-free data structures so that multiple traders could submit their orders concurrently. It would also require kernel bypass to avoid having to pass through an operating system's network stack, and FIX protocol for submitting standard orders to exchanges. The order flow generator is simplified. Real order flow has fat tails, volatility clustering, and informed versus uninformed trader segmentation.

Raft Consensus KV Store

GitHub
The problem

When implementing a consensus protocol from a paper, there is usually no clear way to determine if your implementation is correct. A paper outlines the requirements for the algorithm in terms of its behavior, but it does not address how the potential edge cases of concurrent execution (split vote, stale RPC with an older term number, etc.) will be detected by exception handling. Instead these are represented as invariant failures which would only manifest during adversarial timing; they also are rarely tested through test suites.

The decision

Before implementing a single line of replication logic, I wrote five Raft safety property tests: Election Safety, Log Matching, Leader Completeness, Quorum (a minority partition cannot elect a leader), and Convergence after a partition heals. Each test runs with the Go race detector, and passing via go test -race verifies that the concurrent code is safe under Go's memory model. My in-process test cluster captures communications at the transport level, allowing me to simulate network partitions and drop specific RPCs without worrying about port allocation. Because the HTTP transport and test transport share the same interface, the same Raft node codebase is used for both.

What I'd change

All nodes keep their logs in memory, so when a node fails, its log data is lost. Adding a persistent write-ahead log with CRC32 checksums and fsync after each entry is the most important missing piece. Without it, crash recovery requires catching up from the leader from scratch, and the safety properties only hold as long as every node stays up. That is exactly the condition a consensus protocol is designed to handle.

Delivery Order Router

GitHub
The problem

If an order is dropped during a delivery process, that is significantly worse than if an order took longer to complete. In most implementations, the routing algorithm does not check whether the dasher currently has capacity before assigning an order. Under heavy concurrent loads, some orders will either be double-assigned or simply drop off entirely. Since there are no obvious indicators of failure, such as exceptions being thrown, dropping off may go unnoticed.

The decision

Before writing any routing logic, I locked in two invariants. First, every order must be assigned exactly once. Second, no dasher can ever exceed capacity. The 6-test suite executes these checks immediately after every assignment round. The 1,000-request benchmark ran zero violations. The 1,211 req/s came from getting the data model right, not from optimizing for speed.

What I'd change

Right now the router picks the least-loaded dasher, ignoring location entirely. A better version would factor in dasher distance and delivery radius to minimize total cost. The two invariants stay the same -- every order assigned exactly once, no dasher over capacity -- but the assignment quality improves.

Distributed Generation Portfolio Monitor

GitHub
The problem

Determining anomalies within a fleet that includes solar panels of varying capacities is a much harder problem than it appears at first glance. A 5 kW rooftop panel and a 500 kW commercial array have completely different production profiles. Any single threshold value that effectively detects anomalies for larger assets will be blind to failures occurring on smaller ones. A naive monitoring system on this type of fleet detects 0 out of 3 artificially induced faults.

The decision

I segmented the assets into capacity classes before calculating the anomaly thresholds. Each class had a unique baseline calculated using its own probability distribution. The benchmark injected 3 known faults throughout the diverse fleet and compared segmented versus naive detection methods. Segmented detected all 3 faults with a false positive rate of 0.003. Naive detected none -- it was not merely less effective; it was entirely ineffective.

What I'd change

Manually splitting assets into small and large classes worked here, but clustering would let the system find its own groupings as the fleet grows. The benchmark also needs seasonal coverage -- winter and summer production profiles are different enough to shift what counts as a real anomaly versus normal variation.

Integration Onboarding Monitor

GitHub
The problem

Malformed integration payloads that reach the database cause cascading failures downstream. Bad data propagates through every system that reads from it, and by the time someone notices, the root cause is buried under layers of dependent failures. The break is silent at exactly the point where it would have been cheapest to catch.

The decision

I made the schema gate the single enforcement point. Every incoming payload is validated before any database write, and nothing bypasses it. Invalid payloads are rejected with a structured error response and logged as JSON per customer, so every rejection is traceable to the customer that sent it. Fifteen tests cover the invariants that matter: malformed payloads never reach the database, well-formed payloads pass through unmodified, one customer’s bad payload cannot affect another’s, and every rejection produces a log entry carrying its customer_id. The benchmark ran 1,000 requests across 20 customers at 67.3 req/s, p50 14.654 ms and p95 18.471 ms.

Webhook Relay & Event Inbox

GitHub
The problem

The gap between a packet being sent and a packet being confirmed received is something most application-layer systems take for granted. An event that is accepted and then quietly dropped leaves no trace, and the caller has already been told it succeeded. A downstream consumer that processes an event twice, or misses one entirely, fails silently in a way that is hard to trace back to its origin.

The decision

Every event is written to PostgreSQL before the acknowledgement goes back to the caller, so nothing is accepted and then discarded. Deduplication is keyed on the source and the idempotency key, which makes a retried delivery safe to send. The delivery worker retries with exponential backoff, doubling the interval on each consecutive failure and dead-lettering after ten attempts. The audit log is append-only and each delivery outcome gets its own row, because modifying delivery records after the fact would destroy the history of what actually happened. Rate limiting uses a token bucket rather than a fixed window, since a fixed window lets bursts through at the boundaries while a bucket refills continuously.
